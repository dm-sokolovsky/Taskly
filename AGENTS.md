# Repository Guidelines

## Структура проекта

Taskly — клиентское приложение на React, TypeScript и Vite. Реализованы добавление, переключение выполнения, удаление и сохранение задач в `localStorage`; интерфейс светлый и адаптивный.

- `src/main.tsx` — точка входа и подключение глобальных стилей.
- `src/App.tsx` — корневой компонент; `src/App.css` — его стили.
- `src/index.css` — общие стили; `src/assets/` — импортируемые изображения.
- `public/` — статические файлы, копируемые без обработки.
- `docs/task.md` — требования и критерии приёмки; `docs/ai-workflow.md` — журнал решений, проверок и состояние для продолжения. Обновляйте журнал после каждого завершённого этапа, различая проверки агента и подтверждённые проверки Дмитрия.
- `vite.config.ts`, `tsconfig*.json`, `eslint.config.js` — конфигурация инструментов.
- `dist/` — результат сборки, исключённый из Git. Каталога тестов пока нет.

## Команды разработки и проверки

Запускайте команды из корня репозитория:

- `npm ci` — установить зависимости согласно `package-lock.json`.
- `npm run dev` — запустить сервер разработки с обновлением страницы при изменениях.
- `npm run build` — проверить TypeScript и собрать приложение в `dist/`.
- `npm run lint` — проверить код через ESLint, включая правила React Hooks.
- `npm run preview` — просмотреть предварительно собранное приложение локально.

При изменении зависимостей обновляйте и коммитьте lock-файл вместе с `package.json`.

## Стиль кода и именование

Следуйте существующему стилю: два пробела, одинарные кавычки в TypeScript, без точек с запятой. Используйте функциональные React-компоненты. Имена компонентов и файлов компонентов — PascalCase (`TaskItem.tsx`), функций и переменных — camelCase, пользовательских hooks — `useSomething`.

Описывайте структуру задачи типом TypeScript. Храните небольшой список в локальном состоянии; дополнительные зависимости добавляйте под конкретную потребность. Отдельный formatter пока не настроен.

## Тестирование

Тестовый framework, команда `npm test` и порог покрытия пока отсутствуют. Перед сдачей изменений выполняйте сборку и lint; они не заменяют проверку поведения.

После реализации проверьте добавление, переключение выполнения, удаление и сохранение после обновления страницы. Дополнительно проверьте пустой ввод, длинный текст, клавиатуру и мобильную ширину. При добавлении автоматических тестов используйте имена `*.test.ts`/`*.test.tsx` и документируйте команду запуска.

## Коммиты и pull requests

Перед итоговым ответом о завершённом этапе сверяйте раздел «Состояние для продолжения» в `docs/ai-workflow.md` с кодом, выполненными проверками и `git status`. После создания или переименования коммита актуализируйте в сводке HEAD и оставшиеся изменения. Такая актуализация может оставаться незакоммиченной до следующего коммита; не создавайте дополнительные коммиты и не выполняйте amend только ради записи хеша. Исторические записи этапов сохраняйте, текущую сводку обновляйте.

Используйте [Conventional Commits 1.0.0-beta.2](https://www.conventionalcommits.org/ru/v1.0.0-beta.2/): `<type>[(scope)]: <description>`. Scope необязателен. Тип пишите в нижнем регистре, краткое описание — на английском, с действием.

- `feat` — новая функциональность, например `feat(tasks): add task persistence`.
- `fix` — исправление ошибки, например `fix(layout): adapt workspace to desktop width`.
- `docs` — документация, `refactor` — изменение структуры без изменения поведения, `perf` — производительность, `test` — тесты, `chore` — обслуживание проекта.
- `style` используйте для форматирования кода; визуальные изменения интерфейса классифицируйте по назначению (`feat` или `fix`).
- Необязательные тело и подвал отделяйте пустой строкой. Нарушение обратной совместимости описывайте через `BREAKING CHANGE: <description>` в начале тела или подвала.
- Один коммит должен отражать одно логическое изменение. Историю существующих коммитов не переписывайте без явного поручения.

В PR указывайте цель, изменения и выполненные проверки. Прикладывайте скриншоты изменений интерфейса и ссылку на issue, если он есть. AI-сгенерированный код проверяйте самостоятельно; при сдаче задания опишите использованные инструменты в README.
